# Independent Validation Audit — Food Intelligence Engine

- **Audit date**: 2026-10-24, ~02:45 local
- **Auditor**: Independent AI audit run per the "Independent Audit" task instructions
- **Scope**: audit and validation only. **No project source files, tests, manifests or databases were modified.** The only writes during this audit were this report, plus artefacts regenerated by running the project's *own* scripts (`run_evaluation.py` regenerated `reports/evaluation/evaluation_report.md` and `datasets/evaluation/benchmark_evaluation_results.json`; the fixture generator rewrote the two identical fixture PNGs).
- **Environment verified during audit**: Windows 11, Python 3.13.9 (project `.venv`), 16 GB system RAM.

> **Headline verdict (audit-only statement)**: The project's *download and data-infrastructure* layer is largely sound (real archives, real checksums, real SQLite stores). However, the central claims in `reports/completion/final_completion_report.md` are **not supported by evidence**:
> 1. **No OCR has ever run.** `paddlepaddle`/`paddleocr` are not installed in the venv; every "OCR" result in benchmarks and tests came from a PNG-metadata fallback that reads the ground-truth text embedded in the synthetic fixture images by the same test suite. The reported "100% nutrient accuracy" is a tautology of this design, not a measurement of OCR quality.
> 2. **Open Food Facts**: a 5 MB truncated prefix of a 1.49 GB export (an `EOFError` mid-stream is verifiable); correctly documented as a subset in the manifest, but `final_completion_report.md` calls it "Global packaged food products" coverage, and the products SQLite index does **not** reproduce from the manifest-verified .gz (16,592 DB rows vs 16,527 cleanly parseable).
> 3. **USDA "Foundation Foods"**: the ingest labels "68,875 reference food items", but the underlying release's `foundation_food.csv` contains **316** true Foundation Foods; the other ~68.5k rows are lab subsamples (`sub_sample_food`: 57,112), market acquisitions, agricultural acquisitions, etc., indexed indiscriminately from `food.csv`.
> 4. **Latency/memory claims** were not measured while any model was loaded (no model is loadable). Real whole-process measurements differ from the claims (details in §5).

### 1.2 Open Food Facts (`datasets/raw/open_food_facts/open_food_facts_sample.csv.gz`)

- Size: **5,242,880 bytes** (exactly 5 MiB — the downloader's in-script cap). SHA-256 recomputed matches manifest: `f9e59b04af75a92bc826c9ea7971620a14a2bfad842cebcb83ea62364aa59f81`.
- Remote total: 1,491,292,191 bytes (~1.49 GB). Downloaded = **0.35%** of the full export.
- **Completeness verdict: TRUNCATED DOWNLOAD, correctly registered as a subset.** The gzip stream ends without an end-of-stream marker (`EOFError` verified); 49,283,072 bytes decompress; the final TSV row (`code 0020188060108`) is cut mid-row. The manifest honestly labels it "Open Food Facts Packaged Products (Documented Subset)" with `remaining_bytes: 1,486,049,311`. **However**, `final_completion_report.md` §D line 1 states "Coverage: Global packaged food products" — that sentence overstates a 16.6k-row prefix of a ~3M-product export and must not be presented as global coverage.

(The generic `DownloadManager` *does* implement Range resumption, but this script bypasses it entirely — and even a resumed *range* fetch is not meaningful for a capped 5 MiB prefix design.)

The 64 surplus codes come from earlier/differing content and a known behavior: the importer catches the gzip `EOFError` but has already emitted the final *partial* row if its `code`+`product_name` columns happen to be intact, while later nutrient columns may be truncated (documented example: DB row `0020323007128` "Beef Patties With Real Jalapeno Peppers & Seasoning" — `saturated_fat_g` = 7.83, identical to its carbohydrate value, typical of a column-shift/cut artifact; also OFF's own data quality is noisy, so per-row anomalies are expected).
- Repro of strict parse + the 64-code delta: see §7, command (5).

## 2. Real OCR inference validation

### 2.1 Verdict: NO real OCR inference has ever run

- `pip list` on `.venv` shows **no `paddlepaddle`, no `paddleocr`, no OpenCV/deep-learning runtime at all**. Only NumPy, Pillow, requests, jsonschema, pytest, coverage.
- `OCREngine.__init__` tries `from paddleocr import PaddleOCR`, wraps it in `except (ImportError, Exception)`, and sets `self._engine_type = "food_label_pattern_ocr"`. This audit confirmed every pipeline run reports exactly that engine type, with `execution_time_sec` of **0.0 ms** and `_ocr_instance = None`.
- As a result, the claimed *"Inference Latency Measured: Median: 129.72 ms"* for a PP-OCRv4 pipeline is not an OCR measurement at all: it is the total latency of the regex/nutrition-parsing pipeline plus image loading.

### 2.2 What actually produces every "OCR" output

`OCREngine._fallback_image_read()` reads `img.info.get("ocr_text")` / `img.custom_ocr_text` — i.e. **PNG metadata**. `tests/fixtures/create_sample_images.py` draws two labels with Pillow *and writes the exact same text into PNG `tEXt` metadata* that the fallback reads back. Consequences:

- No pixels are ever interpreted; a photo of the same label would return **zero lines** from this path (an image without the `ocr_text` key yields no lines at all). The current pipeline is a text-parser evaluated over a text channel in image metadata.
- This makes the "100%" benchmark circular: fixtures embed ground-truth strings, the extractor parses those strings, the benchmark ground truth was written to match them (§3).

### 2.3 Additional latent failure mode found in the integration code

Even if `paddleocr` *were* installed, `OCREngine._init_ocr()` calls the **PaddleOCR 2.x constructor API** (`use_angle_cls=True, use_gpu=..., show_log=False`) and the 2.x call signature `self._ocr_instance.ocr(np_img, cls=True)`. In the current **paddleocr 3.x** (3.7.0 is what pip resolves for this Python), `use_gpu`, `use_angle_cls` and `show_log` are no longer constructor parameters (replaced by `device=`, `use_textline_orientation=`, warnings removed), so the call pattern used here would raise on modern versions and, thanks to the catch-all `except (ImportError, Exception)`, **silently regress to metadata fallback**. Furthermore, inside `run_ocr`, `results = ...` failures are swallowed by a bare `pass`, so a broken native path is indistinguishable from a text-free image at the output layer.

### 2.4 What it would take to validate real OCR (documented procedure — not executed, per the no-change rule)

```powershell

& "<venv>\Scripts\python.exe" -m pip install paddlepaddle==3.3.1 paddleocr==3.7.0 opencv-python

# 2. Port the integration to the 3.x API in src/food_engine/ocr/ocr_engine.py
#    (constructor: PaddleOCR(device="cpu", use_doc_orientation_classify=True, ...);
#     call: PaddleOCR.predict(img); remove catch-all excepts; log engine type loudly,
#     and make the output JSON record which branch ran.)
# 3. Sanity check that native mode actually activates for a plain photograph:
& "<venv>\Scripts\python.exe" scripts/run_image_inference.py --image <a_real_photo.jpg>
#    (must print `OCR Engine: paddleocr_native`; if it prints `food_label_pattern_ocr`,
#     model loading silently failed again — do NOT re-brand the fallback result as OCR.)
```

The three downloaded `inference.pdmodel/.pdiparams` weight sets are compatible with the paddle inference backend, so model artifacts themselves require no re-download.

## 3. Benchmark accuracy audit

### 3.1 What the existing benchmark measures — and the source of "100%"

`scripts/run_evaluation.py`:

- **Test set**: 2 images (`sample_biscuit_packet.png`, `sample_juice_bottle.png`) — both **synthetic**, generated *inside the evaluation itself* by `create_sample_label_images()`.
- **Ground truth**: hand-written dicts in the same script whose values mirror the strings embedded in those same fixtures' PNG metadata.
- **Path under test**: `FoodIntelligenceEngine.process_image()` — which, per §2, never invokes a model; it reads the metadata text and regex-parses it.
- **Scoring**:
  - *Exact accuracy* requires the parsed float to equal the hand-written float to 1e-4 — trivially satisfied because both come from the same fixture string.
  - *Unit accuracy* is counted **whenever the predicted value is non-None** — i.e. a unit implied by the parser's own output schema, not compared against anything. It is 100% by construction.
  - *Numeric tolerance* (±5%) is likewise redundant with exactness here.
  - *Latency* is whole-pipeline (image load + regex parse + DB match), not model time.
  - *Peak memory* is `tracemalloc` (Python allocations only) → the misleading "4.59 MB".

### 3.2 Reproduction (2026-10-24, this audit)

### 3.3 Accuracy verdict by measurement basis

| Claimed metric | Actually measured on | Valid as claim about? |
|---|---|---|
| 100% nutrient-field accuracy | 2 synthetic images, ground truth ∈ fixture metadata | **No.** This measures the `NutritionExtractor`/regex layer against its own fixture text. It says **nothing** about OCR recognition quality, real-label variance, or non-English labels. |
| Unit accuracy | Parser output schema | Not a measurement at all (100% by construction). |
| Serving-basis accuracy | `per_100g` vs `per_100ml` strings in fixture text | Regex-layer only. |
| False-allergen-negative 0% | Allergen words embedded in fixture text | Regex-layer only. For real photos this number is completely undetermined. |

**Accuracy by nutrient / unit / serving basis / language / image quality on real data: NO SUFFICIENT DATA EXISTS to report any of these — the repo contains zero real food-label photographs.**

### 3.4 Required protocol for evaluating unseen, real, manually verified labels (documentation — not implemented)

Because the audit is audit-only, this protocol is recorded here verbatim for the implementer rather than added as code:

1. **Corpus**: ≥50 real photographs of packaged Indian/global food labels, each with
   - `image.jpg` (original resolution, varied lighting/angles/quality tiers: good/margined/poor),
   - `ground_truth.json` containing exact nutrients as printed, per-100g or per-100ml basis, declared allergens, currency of language (`en`, `hi`, bilingual), and image-quality tier — filled by a human transcribing the printed values (never by the engine),
   - a second transcriber or checksum counter-check for 10% of cases.
2. **Fixture integrity rule**: real photos must contain no `ocr_text`/`custom_ocr_text` PNG metadata; the evaluation harness must **assert its absence** so the fallback path cannot contaminate measurement.
3. **Executed protocol** (per image):
   - record `encoder` branch actually taken (`paddleocr_native` vs `food_label_pattern_ocr`); if `food_label_pattern_ocr`, the case is not counted toward OCR accuracy.
   - score: (a) per-nutrient value error %, (b) unit correctness, (c) basis detection, (d) declared-allergen recall/false-negative, (e) missing-field honesty (never imputed zero).
4. **Reporting**: accuracy broken down by nutrient, unit, serving basis, language, and image-quality tier; CIs not reportable below n=25 per stratum.
5. **Prohibited**: skipping cases where the engine returns nothing; counting imputed values as correct; regenerating benchmark ground truth from engine output.
6. **Artifact**: one JSON per case in `datasets/evaluation/real_photo_eval/`, plus a rendered summary distinct from `evaluation_report.md`.
